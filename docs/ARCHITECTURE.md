# Application proxy architecture

English | [简体中文](ARCHITECTURE.zh-CN.md)

The Application Traffic page owns a list of application rules. Each enabled rule binds to either `regular` (Mihomo rules) or one actual Mihomo strategy group. The backend validates that a fixed binding is an active group, creates one loopback managed Mihomo listener per distinct strategy, and compiles each rule's helper `proxy_group_id` from the resulting listener map. Applications sharing a strategy share a listener; ports and helper IDs are generated by the backend, not supplied by the UI. The primary `regular` listener is retained while the helper runs so a change from one fixed group to another does not depend on the old group remaining available.

The Verge configuration generation path merges the desired managed listeners into its runtime configuration by name. The controller checks the loaded listener name, port, and fixed group before reporting `proxy_ready`. It also requires helper authentication, helper readiness, the expected `rules_revision`, a live process, and a stable configuration-update epoch. The UI cannot infer readiness from an open port alone.

Clew runs as an elevated, headless helper. Verge remains an ordinary-privilege UI process. A per-start credential file with restricted Windows ACL is used for loopback helper control; the token is not passed on the command line or logged. The helper receives a versioned atomic rules-and-proxy-groups update. On normal update, the backend stages new listeners, publishes and confirms the helper revision, persists rules, then retires unused listeners. A known failed publication restores staged listeners; an unresolvable publication or rollback stops the owned helper and reports a failed/degraded state instead of claiming readiness. Start, rule mutation, and stop share a controller lock.

Only this Verge instance's helper, credential and named listeners are in cleanup scope. The internal-test build has a separate app identifier/data directory and disables system-proxy writes and upstream updates. Profile/subscription switching is rejected while application proxy is running; hot profile migration is not an accepted capability. After exit, saved rules remain but forwarding does not auto-start.

Telemetry has two distinct sources: when the helper is running, the page queries its intercepted TCP data; when it is stopped, a read-only Windows process/TCP snapshot shows system connections. A helper telemetry failure is surfaced rather than silently replaced by direct-system telemetry.
